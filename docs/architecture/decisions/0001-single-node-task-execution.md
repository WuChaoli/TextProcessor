# ADR-0001：单机部署下的任务执行架构

- 状态：已接受
- 日期：2026-08-05

## 决策

1. 当前按单机、单实例设计，每个实际服务使用一个容器，不考虑横向扩容。API 与 Task Runner 独立运行；Task Runner 在一个容器内运行 Celery Worker 与 Celery Beat。

2. 轻型任务的目标处理时间不超过 500ms，由 FastAPI 通过 `async/await` 调用 service、processor、adapter 或外部服务，并在当前请求中直接返回。Route 只负责鉴权、校验和协议适配，不得实现业务逻辑；不得使用 FastAPI `BackgroundTasks`。阻塞或 CPU 密集工作不得直接运行在事件循环中。

3. 计算密集、I/O 密集、GPU 密集、超过前台时间预算或需要可靠重试与恢复的重型任务统一交给 Celery。API 入队后返回 `task_id`，调用方通过 GET 查询状态和结果；重型算法按需建立独立能力服务。

4. 允许使用 `async + Celery` 组合模式：前台通过 Redis 等完成原子校验或资源预占并立即返回，Celery 继续处理库存、订单等后续业务。组合模式必须保证幂等、可靠投递和失败补偿，不能在前台操作成功后以不可靠方式临时入队。

5. 优先使用 TextProcessor Celery 作为后台任务队列。外部服务已有异步协议，或单项重型业务需要独立资源控制和故障隔离时，允许增加额外队列；新增内部队列应保持轻量，优先使用基于 Redis 的队列。

任务采用轻型、重型或组合模式，由 API 契约预先确定，不根据单次实际耗时动态切换。未来若引入多机部署或横向扩容，应重新评审本 ADR。
