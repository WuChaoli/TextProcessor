# ADR-0001：单机部署下的 API、队列与能力服务边界

- 状态：已接受
- 日期：2026-08-05

## 背景

TextProcessor 当前以单机部署和简化容器结构为主要方向。系统需要同时支持前台等待结果和后台查询结果两种调用方式，并根据业务负载决定任务是在中央 Worker 内执行，还是交给独立能力服务。

## 决策

1. 当前按单机、单实例部署设计，每个实际服务使用一个容器，不考虑横向扩容。

2. API 与队列执行层保持独立：
   - API 容器负责流量接入、请求校验、任务入队和结果查询。
   - Task Runner 容器负责队列消费，并在同一容器内运行 Celery Worker 与 Celery Beat。
   - API 容器故障不影响已经入队或正在执行的任务。

3. 所有业务任务均通过队列分发。优先使用 TextProcessor Celery 作为统一队列，但不将其规定为不可突破的唯一队列：
   - 接入外部服务时，允许适配外部服务已有的异步任务或队列协议。
   - 单项业务较重、需要独立资源控制或故障隔离时，允许在能力服务内增加队列。
   - 新增内部队列应保持轻量，优先考虑基于 Redis 的轻量队列，并避免无必要地复制完整任务状态和复杂编排能力。

4. API 提供两种明确的调用协议，但二者都先将任务放入队列：
   - 前台等待模式：FastAPI 入队后轮询 PostgreSQL 中的任务状态，在约定超时内等待完成并直接返回业务结果，不向调用方暴露后台轮询过程。
   - 后台任务模式：FastAPI 入队后立即返回 `task_id`，调用方通过 GET 接口查询任务状态和结果。
   - 执行模式由 API 契约预先确定，不根据单次实际耗时动态切换。

5. 任务实现按资源负载划分：
   - 依赖轻、资源占用可控的任务直接在中央 Celery Worker 层实现。
   - 计算密集、I/O 密集、GPU 密集或依赖隔离要求高的重型任务建立独立能力服务，由 Celery Worker 负责调用和编排。

## 结果

该决策优先减少单机部署下的容器和队列复杂度，同时保留 API 与任务执行的故障隔离。未来若需要多机部署、横向扩容或将能力服务建设为共享平台，应重新评审本 ADR。
